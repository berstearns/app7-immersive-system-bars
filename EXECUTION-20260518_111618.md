### JNI mangling gotcha (fixed in this slice)

**Initial assumption (wrong):** every `_` in the C symbol becomes `_1` (JNI spec §11's escape).

**Reality:** the `_1` escape only applies to underscores in the **original Java identifier** — NOT to the separator characters the mangler inserts when converting `.` → `_` between package segments. The package `pl.czak.learnlauncher.domain.native` has no underscores in its segments, so the prefix is plain `Java_pl_czak_learnlauncher_domain_native_App7Native_`.

The first build had `domain_1native` in `JNI_FN`; runtime emitted `UnsatisfiedLinkError` and helpfully logged the symbol it WAS probing for. Fixed by dropping the `_1` from the macro. Verified empirically: rebuilt `.so` has the correct symbols and the smoke test passes.

### Desktop loader (`App7Native.desktop.kt`)

- Reads `/META-INF/native/<os>-<arch>/libapp7_domain.so` from the classpath.
- Hashes the content (SHA-256, first 16 hex chars).
- Extracts to `${java.io.tmpdir}/app7-domain-<sha>/libapp7_domain.so`.
- Calls `System.load(absolutePath)`.
- Re-extraction skipped if target already exists with matching size — content-addressed paths prevent shadowed stale extracts.

### Build task (`buildHostNativeLib`)

Single `gcc -shared -fPIC -Os -Wall -Wextra -Werror -std=c11 -fvisibility=hidden` invocation that compiles `domain-core/{src/*.c, jni/app7_domain_jni.c}` into the desktop `.so`. Skips CMake — five source files don't justify a configure step. JNI headers from `$JAVA_HOME/include` + `$JAVA_HOME/include/linux`. Wired into `processResources` so it runs automatically before `:desktopApp:run` or any packaging task.

### SHA-256 comparison (spec clarification)

| Artifact | Size | SHA-256 (first 16 chars) |
|---|---|---|
| APK-embedded (NDK clang, stripped, LTO) | 6,544 B | `c6e1486eddd0bae0` |
| Desktop unstripped (host gcc) | 17 KB | `e5b00836ba809c1f` |
| Desktop stripped | 14,240 B | `31bd0dfa15cd45a6` |

**SHAs differ between toolchains; this is expected, NOT a regression.** The original spec said the `.so` should be "byte-for-byte identical across targets" — that's only realistic with a single cross-compiler (e.g., LLVM with identical flags). Across NDK clang and system gcc the optimizer + linker emit different byte sequences for the same semantics. The **real gate is semantic parity**, which `ParityTest.kt` (Phase 5) verifies and the smoke results above already corroborate end-to-end. The spec's Done-When is updated to reflect this.
